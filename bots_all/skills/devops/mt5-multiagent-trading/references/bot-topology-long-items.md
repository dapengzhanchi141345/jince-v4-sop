- **专属 key 隔离 (2026-09-27 已配齐并验活, 一bot一key 固定不共用):** 4 profile 各挂 `agnes-bot-{default,chief,risk,rd}` provider (api.agnes-ai.cn/v1), key_env 分别 `AGNES_KEY_DEFAULT`(我/default) / `AGNES_KEY_CHIEF` / `AGNES_KEY_RISK` / `AGNES_KEY_RD`, 值在各 profile `.env`。`model.provider` 与 `delegation.provider` 全钉死到各自专属 key (子代理也走专属, 不碰共享池); 保留 fallback_providers (agnes-main/.com + agnes-flash) 仅作失效兜底。key 尾 4 位对照表: default=RC3b / chief=yBL7 / risk=GRQZ / rd=HYTWey(用户后补的新key, 原HYTW双端点401已换), 全 .cn 200 验活, 端到端冒烟 4 profile 均计费走各自 .cn key。**Key 交付后先验后配的铁律不变:** 对 `.cn`/`.com` 双端点各发最小 chat (HTTP + 真 body), 200 也看 body 是真补全; 401 = 该端点作废/未激活, 如实汇报让用户去 Agnes 后台核实, 不猜、不拿共享 key 顶包。**⚠ 补充 (2026-10-04): 验活前先确认 key 属于哪个端点体系 — .cn/.com 互不认号, 一把 .com 专属 key 在 .cn 上 401 是正常端点错配, 不是 key 作废; 验活脚本要对双端点都发请求再下结论。** 验 key 的 shell 脚本必须用完整 key 字面量 — 截断/中间写 `...` 会制造假 401, 先怀疑自己字面量再下"key 作废"结论 (本环境 bash 嵌套引号易炸, 写 .sh 再 `bash file.sh` 最稳)。**新增 key 接进 profile 的落点 (2026-10-04 用户给 4 把 .com 新 key 实操):** 每把 key 只接进一个 profile(不跨 profile 共用), 写 `.env` 新变量 + `config.yaml` 追加 provider 块 + 追加进该 profile 的 `fallback_providers` 列表末尾(主链仍走 `.cn` 专属 key 不动, 最小影响); 写前逐 profile 备份旧 `.env`/`config.yaml`; 追加 provider 块时**务必定位到 `providers:` 节内**(用 `fallback_providers:` 顶格行做锚点插在它前面, 别直接 append 到文件尾 — 文件尾往往在 `plugins:`/`video_gen:` 等其它节后面, append 会落进错误的父节导致不生效), 插完 grep 校验 `next_top_level_key` 位置确认在 `providers:` 节内才算接上。
- **⚠ 新 provider 块追加到 config.yaml 文件尾 = 大概率落进错误父节 (2026-10-04 实测):** 桌面端 profile 的 `config.yaml` 文件尾通常在 `plugins:`/`video_gen:`/`known_plugin_toolsets:` 等其它顶格节后面, 直接 `open(cfg,'a').write(provider块)` 会把新块追加成**那些节的子项**(2 空格缩进被 YAML 解析进最近的前一个顶格父节), 结果 `providers.agnes-com-xxx` 根本不存在、key 接不上而你以为配好了。**正解: 恢复备份后, 用 `fallback_providers:` 这一顶格行做锚点, 在它前面插入 2 空格缩进的新 provider 块(它仍属于前面的 `providers:` 节), 插完 grep 新块行号 < `fallback_providers:` 行号确认在 `providers:` 节内。** 同理: 给 `fallback_providers` 追加条目要用它自己顶格段的末行做锚, 别 append 文件尾。没有 yaml 模块(系统 python 常缺)时全程用文本锚点插 + 行号校验, 不依赖 `yaml.safe_load`。
- **iLink/微信 用户配对 (新号/新号首次接入必做, 否则用户发消息被网关拒 "不认识"/Unauthorized):** 网关起好后用户从微信私聊 iLink bot 发第一条消息 → `logs/gateway.log` 先打 `Unauthorized user: <weixin user_id>`(白名单空) + 生成 pending pairing。操作员: `hermes pairing list` 看 pending code → `hermes pairing approve weixin <CODE>` → "Approved!"。之后用户再发消息即路由进 default profile(计费走 default 专属 key)。user_id 形如 `o9cq802uOL2IXFNyr8_ITt827NKE@im.wechat`(见 `weixin/accounts/<acct>.json`)。免配对法: 预配 `.env` 的 `WEIXIN_ALLOWED_USERS=<user_id>` 后**重启网关**。cron 投微信: `cronjob update` 把 `deliver` 设 `weixin:<user_id>`; 该通道须先真注册进 `channel_directory.json`(用户发过一条)才稳, iLink 仅私聊收得到、群聊收不到。
- **iLink 发信限流 (rate limit) 处理: 收得到但发不出, 日志报 `iLink sendmessage rate limited; cooldown active for Ns`.** 高频手动操作 (如连切模型、连发消息) + 网关自动回信会刷到 iLink 平台侧 30s 冷却。处理铁律: **限流自动恢复 (冷却 30s 一轮, 日志里 cooldown 会 30→21→6 递减), 不要去手动再发信探它** — 再发只会再触发一轮冷却反而雪上加霜。做法: ① 读 `logs/gateway.log` 看最后一条 weixin 事件的 cooldown 数字, 判断是否已过 30s; ② 若已过仍全 fail 才排查 (限流窗口拖长/账号风控), 否则等待 + 下次自动触发 (如 22:00 日报) 再验。这是 iLink 平台侧保护, 不是配置错。
- **网关常驻化 (用户"别自己停了" 的 gateway 侧兜底):** Hermes cron jobs 只在 gateway 进程活着时才发射。本机做法: `hermes gateway install` 装成 Windows 计划任务 `Hermes_Gateway` (登录自启, 需 UAC 批准; 非交互驱动喂 `printf "Y\nY\nY\n"` — 3 个 Y: start now / scheduled task / UAC prompt; 喂完 UAC 弹窗几秒内会自启, `hermes gateway status` 确认 `Gateway process running`)。install 后验证 iLink 真连上: `grep -i "weixin" logs/gateway.log` 看 `[Weixin] Connected` + `✓ weixin connected` 两行。注意 `hermes gateway restart` 在"当前 shell 本身在 gateway 进程里"时会被拒(防 restart loop) — 要重启时直接 taskkill 旧 PID 再触发 `Hermes_Gateway` 计划任务, 或从干净 shell 跑 restart。cron 投递默认 `deliver=origin`(建 job 那个会话), 要改推到微信用 `cronjob update` 把 deliver 设成 `weixin:<user_id>`。
