# 事故风暴分诊循环（cron 播报/定时任务批量报红时的处置纪律）

适用：金策系统一条腿（MT5 执行层 / gateway / 记账层 / 数据管线）出问题后，
同一 30min~2h 窗口内会连续 flush 几十条 cron 报红。逐条全量诊断会烧光预算且重复劳动。
按下列纪律分诊，只把真正的“新故障”提级，其余销账。

## 核心规则（每条 = 规则 + 为何）

1. **同类错误第 1 次才全量诊断，之后一行销账。**
   首次用实数把根因钉死（job body 是否 silent + 数据文件 mtime + 进程活体 + 错误分类），排进根治清单。
   同签名再报只回“第 N 个同类症状，已被 X 方案覆盖”，不重跑诊断。
   为何：同根因的重复播报 90% 是 catch-up 积压 flush，重诊=烧 LLM 预算+刷屏。只有 body 从 silent 翻成非 silent、或错误签名变化才重查。

2. **新错误签名必须先核现状，再分类。**
   报出的错误类 ≠ 之前处理过的类（如 gateway 层 service_manager_unavailable vs 记账层 readonly vs 脚本层 WinError 2）时，先探一次当前状态。
   为何：不同层的“GatewayUnavailable”根因完全不同（服务没起 vs 启动窗内 vs 真抖），拿旧诊断套新错会误判。

3. **旧账/假绿识别：报文体数据时间戳比系统时间落后 >1 天 = catch-up 积压 flush 或缓存假绿，不是活数据。**
   所有“账户/持仓/全链绿/系统活着”断言，一律译成“最后活体实读于 X + 缓存快照”，并用 MT5 实读复核。
   为何：节点/播报读的是 10-x 冻结快照 + 停更的 tick，照念会把 6 天前的 0 持仓当现状，误导撤单/开单判断。停摆期内任何播报的“0 仓/0 单”都不可信。

4. **停摆判定只看盘上实数。**
   日志末行 + 数据文件 mtime（tick_live.json / auto_cycle.log）对 `date` 系统时间；偏差 >24h = 停摆事故（红级单独报），不是“瞬时故障”。
   为何：“MT5 实读 0 品种”有两种根因——终端 IPC 瞬断（可自愈）vs 数据源已冻结 6 天（不可自愈）。先查 tick 文件 mtime：冻结=停摆，新鲜才谈 IPC 抖。

5. **路径/工具突失（解释器/终端/CLI/用户子树）先探机器上下文。**
   hostname + 当前用户 + C:\Users 子树在不在，区分“瞬时故障”与“用户迁移/机器重装”。后者=旧用户下工具链（python 解释器、MT5 终端、gh CLI、keyring 认证）整体丢失，数据盘通常幸存。
   恢复顺序：先重建可运行环境（pip download 验 wheel 匹配当前 python 版本→建 venv 安装）→ 再装/起终端 → 最后补跑确定性脚本。需要用户手的步骤（终端手登、供 token）先报后动，绝不翻旧凭证自补。
   为何：把“机器重装导致 gh/ATE 全没了”当成“某脚本 bug 去改脚本”会空转；凭证类缺口只有用户能补，agent 翻旧 keyring=越权。

6. **一次性闹钟在关键日漏响 → 不等调度器，手动补跑。**
   查 jobs.json 的 next_run_at；关键日已过就手动补跑底层确定性脚本（先读脚本确认只读 + 防误触日期闸放行今天），绕过挂掉的 LLM/gateway 层；判完按原分工派销格/回填。结果落盘文件不存在才算没判成。
   为何：one-shot job 漏了明年才再自动响；但它的底层脚本是确定性 0-LLM 只读，agent 走 terminal 直接跑即可，不依赖挂掉的 gateway LLM 腿。

7. **gateway 抖动三步判。**
   gateway.pid 活体 + gateway-starts.log 末行 epoch + 该 job 最近成功拍。拉起后启动窗内（分钟级）探活撞 deadline 属正常；“新重启 + 其后新失败”两条件齐才点名二次掉线。
   为何：gateway 刚拉起那 1-2 分钟 service_manager 未 ready，dispatch 撞 starting-deadline 是启动窗内正常现象，误判成“又在抖”会白报红。

## 销账口径（回群用，大白话）
- 同类重复：「第 N 个同类症状，已覆盖，不重报」。
- 旧账 flush：「这条是 10-x 积压补发/缓存假绿，非现状；真实账户状态以最后活体实读 X 为准」。
- 新故障：三句式「已做X/验过Y/还剩Z」+ 分级（绿一行/黄攒日报/红立即单独报）。
- 不重复念“等待不丢交易状态”（账户/挂单/净值在券商侧持久），只说还需用户拍板的那一步。
