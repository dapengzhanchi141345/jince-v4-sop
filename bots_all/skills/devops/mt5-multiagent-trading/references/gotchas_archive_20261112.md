## tf_cache 写锁坑（LOCKED 三层根因 + 就地覆盖急救 + handle64 抓现行 + 杀毒嫌疑）
`data/tf_cache/*.npz` os.replace 全 LOCKED。三层根因（按 11-06 排查序）：①**同脚本误重复 spawn（同一程序 2 份实例抢锁/抢 IPC/抢投递队列）**——排查法 = `Get-CimInstance Win32_Process` 按 CommandLine 精确分组 + StartTime 排序, 同日同命令 2 活体 PID = 杀新留旧; **重复进程不止造成 K 线锁, 同窗共现三症（K 线 LOCKED + IPC 争用 + bot-chat 队列卡 4h queue_full）, 杀掉重复份后队列会自消化——队列卡 4h 时先查这族同根, 别去重启消费者**; ②**杀完仍 LOCKED = 间歇读持有者类**——临时 python 进程（cron 脚本/回测 runner）`np.load` 读 npz 不显式 `d.close()`（NpzFile 保句柄至进程退出）, 撞上 replace 窗口即 LOCKED, 进程随后自退 = 事后查无持有者; **治法 = 刷新脚本 _atomic_replace 改抖动态重试（6×4s+随机 0-2s 抖动+replace 前清只读属性）+ 读侧脚本 np.load 后 d.close()**; ③**就地覆盖急救法(11-10 实测)**: os.replace 撞锁(LOCKED)时, 改用 `np.savez(path, ...)` **就地覆盖**(直接对同路径 open 写)往往成功——持有者锁的是「新建/替换」而非「就地截断写」。LOCKED 时先试就地覆盖兜底写盘, 再退内存合并; ④抓现行 = **锁着的同时并行跑 handle64 列 npz 句柄**（`handle64 -accepteula npz` 列持有 PID, 立刻 Get-CimInstance 抓该 PID 命令行）——稍后重查进程已退、命令行丢, 查不到持有者就只能走 ② 治法兜底。handle64 本机已装 `E:/workbuddy/国外模型/hermes/cache/scratch/handle64.exe`（`curl -sL -o ... https://live.sysinternals.com/Handle64.exe` 重装）。**grep 证伪纪律: 先 grep 疑似持有脚本全文（tf_cache/np.load/np.save 0 引用=非持有者）再定位, 别按台账猜的方向连环挖**。影响口径 = LOCKED 文件走 tmp 内存合并兜底（引擎 stale-fallback, 0 交易闸影响, 数据滞后不崩）。⑤**handle64 查无持有者 + LOCKED 持续（同一文件此刻单独 python 写测试却可写）= 内核级占用排查候选, 头号嫌疑 Windows 杀毒实时扫描（占文件不进用户态句柄表, ExclusionPath 常为空）— 下"杀毒"结论前先把所有读 npz 候选脚本全文 grep 证伪; 治本 = 给 tf_cache 加杀毒排除项 = 系统级动作, 先报后动。**
