# 双侧边界铁律（live24 进程与源码 · Hermes × 进化营 · 已写共同体宪章）

进化营（workbuddy 侧）与我方（chief）共享同一实弹引擎 jince_live24.py 与其进程族；边界不清=误杀/越界改码/rc 误判。三条铁律：

## 1. live24 进程重启/杀权唯一归 chief + 看门狗
- 对侧清场/维护脚本**禁 taskkill 该族进程**（误杀=我方实盘链路停摆；"我误杀你侧引擎"越界说明与更正已实发生过一次）。
- 必须杀=总线预告→chief 执行（跨方绝不用进程名匹配杀，只按魔号锁/自己 PID 记录杀）。
- **rc=1"崩溃"先判"kill 还是 crash"**：日志无 Python traceback + 杀源是 chief/看门狗维护=正常 kill 退出码，不是崩（"反复 rc=1 崩"常是我方维护重启被对侧误读成故障环）；crash 判据=有 traceback 或杀源不明。双实例抢盘不存在（"每魔一号"锁+自退保护），多 PID 先读锁 holder 再定性。

## 2. 对侧改 live24 源码=同款 5 步 SOP，谁改谁验活
- 进化营对 jince_live24.py 的构件改动（出场开关/紧锁利参数/harness 等）部署前：给 chief 五验证据归档（同分母 OOS+WFO+净期望），chief 对账 MT5 实读后才认账；"已部署"=执行权归 chief，对侧提案+证据，chief 复核后落账。
- 对侧改动若与"出场位单一赢家"参数冲突=单一赢家优先（输方撤块；并存期输方恒 dry-run 只记行不发单）。
- **对侧研究 harness 出 bug（指标虚高，如反转捕获 88.2%→72.6% 更正）时**：结论方向不变（五验仍维持现役参数）=接受更正+把更正后基线同步进真值链（live_state.json）；我方已依据旧数做的裁定（撤下项等）在更正后复核一遍确认不受影响才关账。

## 3. 讨论对齐后才落地（策略参数类）
- 用户两度纠正："先讨论一致再落地" / "对齐后再执行"=策略/出场参数/开关类实盘改动，先总线对齐件（workbuddy+strategy-rd 双确认回执）再执行；**数据对齐（同分母证据）≠讨论对齐（口头确认）**；对齐期间现状若已是最优参数（对方已激活），就不多此一举再改。
- 用户"立即执行"时也先确认对齐状态，再当场执行（回执到=一枪跑完 5 步 SOP，不拖）。
