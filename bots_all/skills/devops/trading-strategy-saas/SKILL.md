# Trading Strategy SaaS (sellable copy-trading platform)

Package a strategy/bot into a multi-tenant product: an asset manager buys the platform, rebrands it (white-label), and their customers subscribe over a web client and have the bot trade on the customer's own broker account.

## Standing rules (apply to every build)

- **Never custody funds.** The SaaS must never hold customer money. Customers trade on their OWN broker account (server-side MT5 API session, or their own terminal). Revenue model = software subscription + asset-manager revenue share, NOT a pooled fund. This is the red line that keeps it sellable and out of unlicensed-investment territory. State it plainly in every deliverable.
- **Benchmark→land→report is the repeatable loop for "match a top-tier institution" asks.** When the user asks to find the gap vs. international top-tier (Darwinex/B2COPY/eToro/Two Sigma etc.), the cycle is: (1) dispatch a research subagent for a sourced 7-dimension gap report (risk engine, portfolio attribution, execution, data, AI, compliance/settlement, ops/SRE) — every capability flagged 【open-source-replicable / licensed-or-external-infra-only】; (2) land ONLY the open-source-replicable items via TDD, one pure-function module each (reconciliation+audit hash-chain, dynamic VaR/CVaR, Brinson-Fachler attribution, data-quality gate, multi-tenant SLO burn-rate); (3) deliver a formal Word gap-report alongside. The licensed/external items are the LIABILITY LINE and must be stated as out-of-scope, not stubbed: statutory filing (13F/Form PF/MiFID II), dark pools / benchmark-crossing, FIX straight-through to exchanges, clearing-house hookup, and 5000-factor / 75k-CPU data substrates. A white-label SaaS ships the AUDIT-READY底稿 (hash-chain evidence pack, PII salted-fingerprint masking, per-tenant error budgets) so the *buyer's* regulated staff do the statutory filing — the system itself never touches client funds and never auto-files.
- **Client-visible "insight panels" (investor dashboard / risk knobs / attribution / reconciliation / AI review) reuse the same pure-function + thin-endpoint pattern, JWT-scoped under `/api/v1/customers/me/*`.** The module builds its own `APIRouter`, self-registers on import (like the ai/marketplace packages) and main.py triggers it with a bare `from . import insights` — no route code in main.py. Each endpoint: authenticate with `Depends(customer_from_jwt)`, pull the customer's real subscriptions/snapshots/signals, call the pure function, return; insufficient data → flagged result, never 500. LLM-backed panels (monthly AI review) do a SINGLE LLM call with deterministic rules-fallback and an `ai_mode` label — never loop/retry (gateway is RPM-limited). On a smoke test, give a LLM-backed endpoint its FULL configured LLM timeout window (first-token latency under an RPM-limited gateway can be ~30s) before calling it broken — slow-but-healthy, and the rules-fallback means it never 500s; a fast patrol that times out early will mis-flag it. The frontend adds ONE aggregate view (one nav entry, N panels) plus D-layer methods whose offline branch returns honest demo data tagged `offline: true` — the file:// double-click demo must never pretend the backend is connected. Verify new endpoints via a fresh TestClient (login → GET), not the running server: if they 404 there but exist in a fresh import, the running instance predates the patch. (Confirm new paths exist via `app.openapi()['paths']`, not by walking nested routes — see the endpoint-registration pitfall below.)
- **Customer-side billing recon must also emit a Merkle audit anchor.** `audit_merkle_anchor(bundle)` over the customer's ledger rows (root + entry count + per-entry digests) is the settlement-reconciliation selling point for a white-label SaaS (regulator stores root + one entry to prove membership, no full chain). Pair the three-way split check with the anchor and expose both under `/api/v1/customers/me/billing-recon`.
- **Institutional capability modules are stateless pure functions behind thin read-only endpoints.** Each new risk/attribution/reconciliation module is a pure-function library (no DB/network inside the function, deterministic, bad-input returns a flagged `sufficient=False`/`clean=False` result not an exception) with one or two TDD test files, then wired to a thin GET endpoint on an ALREADY-MOUNTED router (`/market/*` for admin/report endpoints) that just fetches inputs from the existing data layer and calls the pure function. Do NOT reach into `main.py` to add routes for these — hang them off an existing router so a fresh `import src.main` still shows them in `app.routes` without touching the engine file. Confirm the new paths actually appear in `app.routes` after the patch; a filter that lists nothing means the router wasn't mounted, not that the route is missing.
- **Build a "ceiling benchmark" doc before mass-upgrading.** When the user asks to "make it the best anywhere" or asks for a 100+ item deep optimization pass, first write out a "Deep Optimization Upgrade Blueprint / Feature Ceiling List" into the project root (with a source line per item), and only after that can you assign P0/P1 to downstream workers. Blanket optimization without a written benchmark degenerates into reimplementation of already-done work. The blueprint is the acceptance checklist, not just a plan. And the standing rule for this class of work: once the benchmark is written, proceed to the ceiling without asking — the user's rule is that "absolutely the most" must be enough; do not request permission at each step, stop only on a genuine blocker (missing credential, a red line such as touching engine directories), and report outcomes after the fact.
- **Integrating an external product/methodology is capability-mapping, not feature-copying.** When the user hands over an external deck/doc/competitor and says 'deep-learn it / fold it into the system', split its selling points by whether YOUR system has the underlying data source: METHODOLOGY that is reproducible on your own data (NL→strategy, a template/parameter marketplace, auto-tune-by-performance, risk gates) gets landed on the EXISTING engine/endpoints/router — reuse the LLM+rules dual-track with an `ai_mode` label for any natural-language entry point, do not build a parallel subsystem; DOMAIN data you don't own (a competitor's indicator library, an alt-data feed, a market it trades that you don't) gets REFUSED — shipping it would fabricate data and break the no-fabrication red line. State plainly which items you integrated and which you declined and why. The failure shape is copying the whole deck 1:1 and shipping features that have no real data behind them.
- **Server-side unified execution is the differentiator — build it first.** The sellable UX is "customer only touches a web page; the platform executes on their account from the server" (one MT5 API session per subscribed customer). Do NOT default to "customer installs an EA on their own terminal" — that is the fallback, not the product. Hand-rolled: a `src/exec/` execution layer that opens a MetaTrader5 session per customer account and mirrors signals through the customer's risk gates.
- **Two execution paths, always.** (1) server-side unified execution (main, web-only UX); (2) client-terminal ZMQ mirror (fallback for customers who won't open server accounts or who want their terminal doing the copy). Ship both; they don't conflict.
- **"The system carries the EA" = an in-process scheduled auto-runner + a persisted three-tier kill switch, NOT a downloadable MQL5 file.** When the user insists the EA lives *in* the platform and the platform runs it for them ("直接带着跑、不用下载"), the shape is: (a) the customer's EA is stored as a config row (symbol pool / style / threshold / protections); (b) a background `asyncio` loop in `main.py`'s `lifespan` (sibling to the gate-sweeper, cancelled on shutdown, each iteration in its own DB session with per-EA exception isolation so one failure never breaks the loop) sweeps `auto_enabled=True` profiles whose `next_auto_run_at` is due and runs them; (c) a `risk_switches` table holds three independent tiers — `global` (ops one-stop), `customer` (per-customer auto-trip), `ea` (per-EA) — where any ancestor tier `tripped` fail-safe-blocks new orders for that scope; the customer tier auto-trips on equity drawdown ≥ style max-drawdown or daily-loss ≥ style daily-loss (high-water baseline ratchets up only, daily baseline refreshes at first run of the UTC day, a daily-loss auto-trip self-resets next day) and is manually releasable. MQL5 export stays available but demoted to *optional* (the in-system runtime is the product). **CRITICAL CORRECTNESS: the scheduled auto-loop MUST call the SAME shared runner function as the manual "run" endpoint (e.g. `run_ea_profile(db, p, auto=True)`), so every pre-trade gate, kill-switch check, and dry-run discipline applies identically to both paths — never give the auto path a thinner, direct-to-plan call that skips the risk gates; that silently un-guards the thing that runs unattended.** Default dry-run (record only, no funds); real orders only when an MT5 account is bound AND the execution env switch is on.
- **Layer an institutional pre-trade gate battery as a pure-function module + per-order orchestrator.** Top-desk practice decomposes into four pillars, each a deterministic pure function (TDD-able, no DB/network inside): ① pre-trade gate battery (fat-finger sanity — stop distance > N×ATR rejects as a typo; spread > k× its rolling average rejects market entries; per-order notional cap; per-symbol concentration; total max positions; free-margin sufficiency); ② tiered kill switch (rule above); ③ news blackout (Tier-1 NFP/FOMC/CPI/central-bank ±30 min, FOMC presser extends the post window to ~60 min, Tier-2 ±15 min; current spread > 1.5× average extends the lead window; UTC-aligned event timestamps); ④ volatility-regime sizing (current ATR ÷ long-run median ATR → multiplier clamped ~0.2–1.0, in-drawdown ×0.7, order entry > 2.5×ATR from reference → stale-order flag). An `evaluate_order`-style orchestrator runs the pipeline in order (resize → kill-switch → news → pre-trade); any hard failure rejects the order but records it (fail-safe: rejected orders are logged with machine-parseable prefixes, never raised as 500s). Two invariants: (a) an execution intent's `risk_ok` must be the gate verdict, NEVER a hard-coded True; (b) a missing input (free_margin=0/None, no equity baseline, no long-run ATR reference, no event source) makes that specific check SKIP honestly (neutral multiplier, gate open) — a dry-run with no live market data must never be blocked by phantom limits or crash on absent fields. Client-tunable protection params (SL/TP/trailing/equity-stop/lots) are a separate PARTIAL-UPDATE endpoint (PUT of a partial dict): merge over the stored row, and treat 0/empty/None as "unset" → fall back to the style defaults — never let a client's 0 overwrite a stored non-zero value (that silently disables the protection); the merged dict flows through `build_order`/`build_auto_plan` so the client's dials actually land on the order fields, and a UI panel of inputs feeding `config.protections` is the front-end shape.
- **The real execution leg is a swappable executor behind ONE Protocol, env-gated and default-dry-run — it must NEVER touch real funds by default.** The engine recognizes only `Executor.submit(intent)->dict`; ship a `DryRunExecutor` (fill = signal price, no real order) as the default and a `Mt5Executor` that calls `MetaTrader5.order_send`. The factory `init_default_engine()` picks via env var: default = dry-run; switch to Mt5 ONLY when `JINCE_SASS_ENABLE_MT5=1` AND `import MetaTrader5` succeeds AND the terminal is online (`mt5.initialize()` true). Any import/initialize failure → honestly fall back to DryRun (log it, never 500, never report a fake fill). Fund-safety clamps stay in the engine risk gate, not the executor; the executor only faithfully places `risk_ok=True` orders and records the real ticket into the audit ledger. This keeps the Linux signal hub from needing the MT5 SDK (which only runs on a customer's Windows execution host) while the go-live code path already exists.
- **Customer-own-account execution leg: the live path has THREE gates, and the MT5 SDK has a physical constraint the design must honor.** Gates: (1) platform env switch `JINCE_SASS_ENABLE_MT5=1` (ops-only), (2) a per-customer live flag (customer-togglable, default False, its own endpoint), (3) the attached terminal's `account_info().login` MUST equal the customer's bound account login — the MetaTrader5 SDK can only `order_send` to the one account its terminal is logged in as, so a bound-account ≠ terminal-account (or unbound, or terminal offline) situation must **honestly degrade to dry-run with the reason recorded on the run log**, never fake a fill and never 500. Any gate missing → effective mode is dry-run, and a status endpoint must tell the customer/operator exactly which gate is missing (global / customer / terminal-match), plus a fill ledger table per customer that records EVERY order — dry-run records included (status `dry-run|sent|filled|rejected`, target login, MT5 ticket on real fills, idempotent client_order_id with a minute-shard so the auto-resident sweep can't double-fire the same direction) — exposed as a reconciliation endpoint so the customer can check each order landed where claimed. Wire the executor into the SAME shared runner the manual and auto paths use, and append the execution outcome to the run record's note so history shows "sent / not-sent-why" per run. **Scaling past one terminal: register execution nodes and route by account, don't clone the hub.** The MT5 SDK constraint (one terminal = one attached account) means a hub serving N customer accounts needs N execution nodes (each = one Windows host/terminal attach), NOT N hubs. Shape that works: a node-registry table (name, attached mt5 login, credential stored-but-never-echoed, status/last_seen heartbeat) + an ordered queue table (one row per routed order, idempotent client_order_id, state pending → claimed → sent/filled/dead); the hub executor routes each order — terminal-attach == bound account → send local; bound account registered on another live node → enqueue on that node (status `routed`, recorded in the fill ledger too); unknown/offline → honest dry-run degrade with reason. The node process polls its own queue (atomic claimed transition prevents two nodes grabbing one order), sends on its local terminal, and reports back; failed reports back off and dead-letter after N attempts, and a replay action resets dead→pending. Deleting a node with a non-empty pending queue must 409, never silently drop its orders.
- **Multi-tenant isolation from day one.** Per-asset-manager namespace (tenant → strategies, customers, subscriptions). Prove isolation with a test that two tenants cannot see each other's data. Retrofitting tenancy later is the expensive path.
- **Client risk gates belong in the copy filter, before execution.** Reuse the 金策 gate ideas: spread gate, per-customer max-drawdown circuit breaker, daily-loss stop, subscription-expired → stop copying. Every executed copy writes an audit row (signal price / fill price / slippage / timestamp) — audit trail is a selling point, not overhead.
- **Real market-data layer, never fabricated K-lines.** The trading panel's candles must come from the real MT5/MT4 platform via `MetaTrader5.copy_rates_from_pos` (all 8 timeframes M5/M15/M30/H1/H4/D1/W1/MN1), not a code-generated random walk. Degrade honestly: terminal up → real pull; terminal down → replay the last persisted real snapshot; no snapshot either → return an empty set with a "terminal not connected / no data" note, NEVER a synthesized candle. Wrap the whole MT5 access path in one global lock (SDK is not thread-safe) and make every call read-only. Before shipping, start the real server and assert all 8 TFs return non-empty `source=mt5` bars — see `references/real-market-data.md` for the SDK shape gotchas (numpy rows, namedtuple deals, `server_time` missing, and **timeframe constant values that differ from the published table**).
- **Ops observability is part of the deliverable, not an add-on.** A sellable platform ships an /admin/metrics endpoint (copy latency P50/P95/P99, reject-rate by reason, double-place detection, dead-letter-queue depth, terminal availability, fee health, WS connections, signal-source heartbeat) + a layered /healthz (db / ws / signal / sweeper each reported separately) + a web ops page with red alert strips. Without it, an asset manager cannot sign a SLA and the platform stops being sellable at the top end. Expose the 8 SLA metrics as a hand-rolled OpenMetrics text endpoint (e.g. `/admin/metrics/prometheus`: `# HELP`/`# TYPE` + labeled metric lines, zero third-party dependency — missing metrics render as `0`, never 500) so a Prometheus scrape + a pre-provisioned Grafana datasource can chart them directly; ship the `prometheus.yml` scrape config and the Grafana datasource YAML in a `deploy/` folder.
- **Payment gate (402) is a first-class acceptance path, not an afterthought.** The copy/subscribe endpoints reject an unpaid/expired customer with business code 402 (copy paused, net-value still readable). Consequence for the acceptance suite: a "register → subscribe" test will hit 402 until the customer has paid, so every subscribe/WS-signal test must first run the `/billing/checkout` (simulated 4242 card) activation step, and cross-tenant 403 tests must also pay the outsider first or the 402 gate masks the 403 assertion. When a billing router is added to the app, confirm it is actually `app.include_router(billing_router)`d — a 402 gate whose `/billing/*` endpoints 404 means the gate was wired into the copy endpoints but the router never mounted. Symptom chain that pins it: subscription returns 402 AND `/billing/checkout` also returns 404 → router not mounted; if `include_router` IS present but routes still 404, the router's own `APIRouter(prefix=...)` doubled the path (endpoints defined with full `/api/v1/...` paths on a router that already carries `prefix="/api/v1"` land at `/api/v1/api/v1/...`) — keep one source of truth for the prefix.
- **Every copied order is idempotent and bounded.** Mint a stable `clientOrderId` per copied trade (`JINCE-{strategy}-{leg}-{signal_ts_ms}`) and check the fills table before executing a retry so a re-sent signal never double-places. Resolve the strategy symbol to the customer's broker symbol through an alias table (+ auto prefix/suffix probe) and reject with a reason rather than guess; clamp lot size to a per-account max-lots and max-equity-% hard ceiling before submission.
- **Compliance-grade audit is a selling point, not overhead.** Keep an append-only audit event with before/after JSON snapshots plus a tamper-evident hash chain (each record hashes its predecessor; verify by recomputing head-to-tail). Also refuse to start in production while built-in dev JWT/API keys are still active (inject real keys, else fail boot) — shipping default secrets is a backdoor.
- **Billing compliance is two-tier: consent + debt.** (a) No copy-trading before a structured consent record: N risk categories checked item-by-item (market/slippage/leverage/liquidity/tech-failure/strategy-change/backtest-limit), with doc version, device, IP, timestamp and SHA-256 hash of the consent text stored; verify before any copy/subscribe and refuse without one — ESMA-style risk disclosure is a red line, a bare checkbox bool does not count. (b) Failed fee collection accrues to a debt table (kind + amount + reason, aging counter), never silently dropped; on next billing cycle / subscription activation the recovery pass auto-collects recoverable debts, and both accrual and recovery leave billing-event rows — uncollected fees are a tracked asset, not a write-off.
- **PWA + local push upgrades the web client without breaking file:// delivery.** Ship `manifest.json` + `sw.js` + `push.js` + two generated PNG icons (PIL: dark background, brand glyph, K-line motif). Gate SW registration AND push init on `location.protocol.startsWith('http:')` so a file:// double-click stays a pure offline-mock demo that never registers a service worker. SW caching policy: never cache API paths (`/api/`, `/market/`, `/admin/` → network only), navigation requests network-first with cache fallback, static app-shell resources **stale-while-revalidate** (return the cached copy instantly, silently refetch + overwrite in the background on success — NEVER bare cache-first: a cache-first app shell that first caches while the server was down / old code is permanently stuck serving the stale copy, the classic "page is blank and F5 doesn't fix it" white screen; stale-while-revalidate self-invalidates the stale copy on the next load). The push module (Notification API + Web Push placeholder) must report its channel as `offline-pending` / not-subscribed when the backend push endpoint isn't wired — it never claims a notification was actually delivered. **Bake the white-screen self-heal into the delivered client rather than instructing the user to clear browser cache manually** (manual `F12 → Application → Unregister` + `Clear site data` is multi-step and the user typically can't do it or says "still doesn't work"): on page load, the inline register script (a) detects a stale SW cache version (`jince-pwa-v<N>`) → deletes that cache + unregisters all registrations + `location.reload()`, gated by a `sessionStorage` heal-marker so it runs at most once (no reload loop); (b) registers with `{ updateViaCache: "none" }` + `reg.update()` so the browser always re-fetches `sw.js` over the network to compare versions; (c) on `updatefound`, when a new SW reaches `state === "installed"` while a controller already exists, auto-`location.reload()` so the user lands on the fixed SW with zero manual steps; and — the critical one — `sw.js`'s own fetch handler must **never** intercept requests to `sw.js` itself (return early / network-only for it): a cache-first `sw.js` intercept means the old SW serves its own stale copy to the browser's registration fetch, the new SW can never install, and the stale cache is locked in forever (the classic SW upgrade deadlock that makes even the self-heal useless). Bump the cache version string on every SW policy change so all existing users' next load reinstalls.
- **A customer-operable feature ships with its usage explanation — an unexplained feature is an unfinished deliverable.** When the deliverable includes anything the customer/operator runs themselves (custom EA configs, live-trading toggles, execution-node registration, tenant admin console), pair it with a plain-language guide: what the feature is in one line, the step sequence (login → configure → run → tune → go-live), who controls each gate (platform-side switch vs customer-side switch vs deployment-side account attach), and the safe defaults (dry-run, fail-degrade). A "feature exists but nobody can use it / no one knows how" is the rejected shape — so before declaring a feature done: verify it is actually LIVE on the running service (router mounted, panel wired, endpoint returns 200 on the real port with a real login), and hand the usage guide alongside. "Can't use it" reports about a working feature are usually a mount/wiring miss, not missing logic — probe the live endpoint first, then explain. For a 'no output yet / nothing triggered' feature (a strategy scanner, the auto-trader), pair the guide with a one-click DEMO button that forces a GUARANTEED result — drop the threshold, widen the symbol set, allow both directions — and render the full end-to-end run (score, SL/TP, picks, fills) instead of a blank 'no trigger' state; when it does not trigger, show the per-symbol reason (score/bias/no_data). That is the single best defense against the 'looks broken / is just decoration (摆设)' complaint.
- **The demo entry point is part of the deliverable (the user wants to *try* the system).** When the user says "can I log in / connect / let me try the system you just built", they want a zero-config experience, not a connectivity probe — disambiguate first (in this context "can I connect" usually means the demo entry point, NOT the LLM/API gateway; I once misread it as a gateway check and had to be corrected). Deliver: (1) start the server on a fixed port; (2) mount the `web/` client at the FastAPI root with `app.mount("/", StaticFiles(directory=web_dir, html=True))` so `http://127.0.0.1:PORT/` serves the client AND the API same-origin (zero CORS, zero config); (3) make the client auto-detect online mode — `ONLINE = API_BASE !== "" || location.protocol !== "file:"` and WS host = `location.host` when `API_BASE` is empty (a file:// double-click stays offline-mock, an http-served copy goes live); (4) seed a pre-registered login-able demo customer. Hand back ONE url + ONE credential pair.

- **Adding a column to an ORM model that maps to an EXISTING table does not migrate a live SQLite db — SQLite never auto-ALTERs, and the next write to that table crashes.** When you add a field to any table the running service already uses (e.g. a new boolean flag on a run-log table), extend the project's idempotent `_migrate_sqlite_columns()` helper (check `PRAGMA table_info` → `ALTER TABLE … ADD COLUMN`, table-by-table, skip nonexistent tables, no-op on fresh dbs where `create_all` builds everything) and make it table-aware rather than single-table if it wasn't. Skip this on PostgreSQL (fresh `create_all`). Verify by running the migration against the real db file and re-listing the table's columns.
- **A minute-sharded idempotent fill key collides when ONE plan emits several same-tick orders.** The unique-key rule (one key per customer/EA/symbol/direction/minute) assumes one order per sweep cycle; an auto-plan with multiple picks or a multi-leg style emits 2+ orders of the same symbol+direction in the same tick, and inserting the second row violates the UNIQUE constraint on the fill key, crashing the whole run. A single-order smoke run never reaches this, so only a multi-order regression test catches it. Add a per-order sequence suffix within one run (`...-{minute}-{seq}`): distinct fills of one run stay unique, while the same seq at the same minute across runs still yields the same key, so the double-fire protection is unchanged. Lock it with a test: a plan of 2 same-symbol same-direction orders records 2 rows without IntegrityError.
- **Verify a persisted change by EXACT ID, not by list position.** Reading back `GET /list` and grabbing `profiles[0]` after a create/update validates the WRONG record (list order is arbitrary and earlier test runs leave other rows). Fetch by the returned id and assert the field you just changed — that is the only proof the update landed. **And a mutation endpoint that flips a row must `db.commit()` (+ `db.refresh(obj)`) BEFORE returning** — a toggle/enable endpoint that echoes the live-session ORM object reports `True` to the client while the db file still holds the old value, because the session closes without committing. Symptom: API says on, the background sweep never fires, raw SELECT shows 0. The fix's proof is a FRESH connection's SELECT (sqlite3 read of the row), never the API echo — the echo only proves session state.

- **A JWT auth dependency that opens and closes its own session returns a DETACHED ORM instance — mutating it in the endpoint and `commit`/`refresh` on a different local session 500s.** `customer_from_jwt` builds the Customer, closes its session, hands back the orphan; a mutation endpoint doing `me.flag = x; db.commit(); db.refresh(me)` crashes on refresh of the detached instance (echo paths can still look fine in-process). Re-fetch first: `c = db.get(Customer, me.id)` on the endpoint's own session, mutate/commit/refresh/return from `c`, never from the injected object. The same detach applies to a row YOU read on a session you have since closed — a read-only fetch whose session is now closed is detached too, so a later write (e.g. a `?apply=true` write-back of a tuning suggestion) must open a FRESH session and re-fetch the row by primary key before committing; committing on the stale closed-session object silently no-ops or raises.

## Pitfalls (cost time if ignored)

- In a module-scoped TestClient acceptance suite, tests that depend on earlier-test state (e.g. WS-push needs an active subscription, which a later unsubscribe test tears down) pass standalone but fail in full-suite order. Make each test self-seeding (re-check + re-subscribe before asserting) rather than relying on cross-test state, or the suite becomes order-fragile and every added test breaks an old one.

- A WebSocket push test that asserts on the *structure* of messages **inside** its receive loop is flaky: any malformed/half message (e.g. the pump is mid-restart and emitted a partial record) throws, the `with` block exits early, and the collected list is still empty → a false "no signal received" failure that 1 of N runs passes, the rest fail. Split it: the receive loop only *collects raw text* (swallow `WebSocketDisconnect` AND any other exception, keep looping to the window end, several rounds), then parse + validate structure **after** the window, and give the window real headroom (a demo signal source that ticks every ~0.2s still needs ~30s×3 in a TestClient, not 15s, because the client event loop starts the pump lazily). Validate structure post-collection, never in the hot loop.

- Don't confuse "selling a PAMM/white-label platform" (the commercial model, e.g. B2COPY/Tramaxis, closed-source, ~€799/mo) with "a copy-trading repo on GitHub" (usually crypto Solana/Hyperliquid bots or name-collision hits). Screen repos by active `pushedAt` + correct `language` + non-archived + a README that actually matches MT4/MT5 copy trading — star count and description are unreliable.
- Do not mix vendored open-source into the main git trunk. Clone shallow into `vendor/`, keep it out of the product repo, and preserve original author attribution in the delivery README for MIT/Apache-2.0 components.
- **When containerizing the SaaS, `.dockerignore` MUST exclude the trading engine and the Windows timed tasks — the image/stack only ever contains the SaaS app directory.** The 'never touch the engine / never mix in other tasks' ironclad rule extends to build artifacts: a `COPY . .` that pulls in the out-of-scope engine or scheduled jobs silently bundles forbidden code into the sold image. Ship a one-click `docker-compose.yml` (API + Prometheus + Grafana, default dry-run); when the host has docker CLI but no running server, DELIVER the files + validate (YAML syntax, build config, endpoint probes) rather than pretending to build — state plainly that `docker compose up -d` on a real host is the go-live step.
Do not hand-roll the MT4/MT5 terminal mirror layer when a proven MIT/Apache component exists (see references) — but DO hand-roll the web client, admin portal, and billing engine; those are closed-source commercial only and are exactly the value you sell.
- **When you build a strategy-quality / composite score (Darwinex D-Score / ZuluRank style), do NOT let raw win-rate dominate the weighting.** High win-rate is a fake signal: a strategy that scrapes many tiny gains while risking one catastrophic loss looks great on win-rate but is the worst thing to copy. - **A "can't log in / 登录不上" report is usually a stale pre-filled credential, not a broken endpoint.** The demo client pre-fills the email field with a remembered address from a prior session; if that account was never registered (or the DB was re-seeded), the login 401s while your `curl` to a *known* seeded account returns 200 — the server is fine, the credential just doesn't exist. Diagnose by (a) capturing the form's actual field value + current hash in the user's browser (a headless form dump, or `list_windows` + capture of the real Edge tab), and (b) querying the `Customer` table for what actually exists; fix by registering the pre-filled email or handing the user the seeded one. **When that account's username contains CJK characters, do NOT build the register body in a git-bash `curl -d '{"username":"总管家",...}'` — MSYS re-encodes the UTF-8 body and Pydantic rejects it with 400 "There was an error parsing the body" (a parse error, not validation, so it looks inexplicable).** Register via Python instead: `json.dumps({...}).encode('utf-8')` as the request body + `Content-Type: application/json`, which delivers the CJK intact.
- **A demo/synthetic data generator that runs on a recurring pump tick must be BOUNDED, or it silently poisons the persisted DB and every downstream metric.** A signal-source `equity_step(base)` that does `base * (1 + drift)` with a net-positive drift, called every ~3s by the pump, compounds to ~1e16 within tens of thousands of ticks; the persisted `EquitySnapshot`/`Strategy.net_value` then feeds absurd figures into attribution ("+361%"), drawdown ("100%"), volatility (~1e14), and any VaR/quality-score panel — and the corruption is permanent in `data/app.db`, surviving restarts. Build the demo step as a bounded random walk: add a per-step noise (in the natural units, not a percentage multiplier), pull back toward a neutral level (mean-reversion), and hard-clamp to a sane band (e.g. net value stays within [50,500] base points). If a polluted DB already exists, stop the service, delete the out-of-band snapshots + reset the aggregated `net_value`, and restart so the bounded generator starts clean — don't just patch the generator (the bad rows keep serving).
- **Do not guess endpoint paths from router variables.** The market router is mounted at root `/market/*`, NOT `/api/v1/market/*` (marketplace is `/api/v1/marketplace/*`). Confirm against `/openapi.json` instead of inferring from the router's `prefix=`.
- **Killing the service on Windows via git-bash: `taskkill //PID <pid>` reaches taskkill literally as `//PID` and fails ("invalid argument") because MSYS path translation is disabled for native tools.** Use the native single-slash form `taskkill /PID <pid> /F`.
- **Windows built-in console tools emit GBK-encoded output; Python `subprocess.run(..., text=True)` under a C locale decodes it as UTF-8 and crashes (UnicodeDecodeError on high bytes), or gets `None`/empty stdout when a tasklist filter matches nothing — a silently fatal failure for any process-liveness check.** Read such output with `encoding="gbk", errors="ignore"` and guard with `(r.stdout or "")`. The mechanism that makes this expensive: a watchdog whose liveness probe throws on one run dies every cycle, so the very thing it exists to keep alive (service + tunnel) never auto-restarts. Also: on this host PowerShell applets (`Get-NetIPAddress`, `Get-CimInstance`, bare `cmd /c`) routinely hang past timeouts — use git-bash-native `ipconfig`/`netstat`/`tasklist`/`wmic` instead, and parse `wmic /format:list` with a regex split on `ProcessId=(\d+)` (pid and commandline land on SEPARATE lines, so line-grep misses everything). Judge taskkill/PowerShell success by exit codes, not by the mojibake text. See `references/remote-customer-access.md`.
- **When the customer service runs on its own port that you must NOT restart without consent, verify new endpoints on a FRESH alt-port instance: kill only the zombie holding the alt port (find it via `netstat` first — an orphan of OLD code silently holds the port so your restart serves stale bytes and every endpoint 500s), then start a new instance with the new code and drive it with clean UTF-8 JSON from Python (`urllib` + `json.dumps(...).encode()`), never `curl -d` from git-bash (MSYS mangles CJK/UTF-8 bodies → spurious 400s).**
- **A persisted auto-scheduler column (`next_run_at`/`next_auto_run_at`) crashes the background loop on its first due-check with `TypeError: can't compare offset-naive and offset-aware datetimes`.** A `utcnow()` helper that returns aware-UTC datetimes writes fine, but SQLite DATETIME columns read back NAIVE (tz is not stored). Compare a read-back value to `now` only through a normalizer (naive → `replace(tzinfo=timezone.utc)`), and reuse that helper on both read paths — otherwise the loop dies per-EA or swallows the whole sweep.
- **Restarting a live customer-facing service for a new-code experience session: back up the db file FIRST, then relaunch with the project's venv interpreter, and gate the hand-off on /healthz.** Sequence: copy the sqlite file to a timestamped `.bak` → `netstat -ano | grep :<port>` for the PID → `taskkill /F /PID <pid>` → relaunch with the project venv's python (`.venv/Scripts/python.exe -m uvicorn …`), NOT a bare global/uv interpreter that lacks the app's deps (the service silently fails to start) → poll `/healthz` to 200 before driving any new endpoint or handing the URL to the customer.
- **When you factor a shared runner OUT of a router-builder's local scope into a module-level function, re-import the ORM models at module scope.** Models imported inside `_runtime_router()` are visible only to that closure; a module-level `run_ea_profile` referencing `ClientEaRun` there fails not at import but at RUNTIME — first real request 500s with NameError while every router-local endpoint still works, which masks the bug until the auto-path runs. Grep the new function for model class names and import them at top level.
- **Two service instances sharing one SQLite db (production main port + a verification alt-port on the same `data/app.db`) need a busy timeout on the engine (`connect_args={"timeout": 15}`) or writes intermittently fail `database is locked` under concurrent commits.** Both instances migrate/refresh state rows (kill-switch baselines, run logs), so this bites in the middle of a request, not at startup.
- **A report/metrics endpoint that nests two FULL-table scans in Python goes O(n×m) and becomes the slowest call in the API on production-sized data** (e.g. signals×snapshots 237K×164K → ~27s). Fix that PRESERVES metric semantics: cache a per-key sorted array (per-strategy signal timestamps) at module scope and use `bisect` for range filtering, and replace 'load every row' with `COUNT(*)` + a targeted rejected-rows query — ~27s → ~1s. The smell is a per-request `select list(Signal)` over the whole table; when an endpoint does it, add a cached sorted-timestamp list keyed on the max observed ts and bisect against it.
- **A failed `write_file`/large `patch` can truncate a big file to 0 bytes with no error surfaced** (a partial write or a colliding sibling edit mid-session). After ANY write/patch to a large file, check the byte size (`wc -c` / `os.path.getsize`); on a 0-byte or near-empty result, recover from version control (`git checkout HEAD -- <file>`) and RE-APPLY your pending edits on top — never keep patching a half-written or emptied file, and always re-verify size after the recovery write.
